# Core Data Model

This document describes the principal in-memory data structures and data transformations used by the current backend and frontend. It is a conceptual guide, not a database schema: the application primarily maintains simulation state in process memory and uses a local serialized model cache.

## 1. Weather state

`backend/simulator.py` defines `WeatherState`, the record produced by a simulation step. The backend converts these records into dictionaries retained in `live.rows`.

The retained row fields used by `backend/main.py` include:

| Field | Meaning |
|---|---|
| `timestamp` | Timestamp for the simulated minute, serialized as ISO text. |
| `pressure` | Simulated atmospheric pressure in hPa. |
| `temperature` | Simulated temperature in degrees Celsius. |
| `humidity` | Simulated relative humidity percentage. |
| `light` | Simulated light level in lux. |
| `rain_mm` | Simulated precipitation amount for the step. |
| `raining` | Boolean wet/rain indicator used by the prediction target and status. |
| `scenario` | Scenario identifier associated with the generated row. |

These are synthetic observations generated by the simulator.

## 2. Feature matrix

`backend/features.py` transforms the rolling weather history into 15 model inputs. The feature order is defined by `FEATURES` and must be treated as significant because the trained model expects columns in that order.

| Feature family | Inputs |
|---|---|
| Pressure change and variability | `pressure_delta_10m`, `pressure_delta_30m`, `pressure_delta_1h`, `pressure_delta_3h`, `pressure_accel`, `pressure_std_30m` |
| Humidity | `humidity`, `humidity_delta_30m` |
| Temperature | `temp_delta_10m`, `temp_delta_30m`, `temp_vs_3h_mean` |
| Light / sky brightness | `light_ratio`, `clearness` |
| Time of day | `hour_sin`, `hour_cos` |

The longest rolling lookback is three hours. `HISTORY = 181` is the number of one-minute rows needed to make the longest feature available, including the current row. Initial rows without enough past context contain missing values and are not used for inference/training as valid feature rows.

## 3. Prediction target

`future_wet_label()` creates `rain_next_30min` labels. A row is positive when the wet/rain indicator becomes true during the following 30 minutes. Rows without a complete future window are assigned NaN and are excluded from supervised training/evaluation where appropriate.

The target is an event-within-window label, not a prediction of exact rainfall amount, exact onset minute, or rainfall duration.

## 4. Probability history

`Live` stores one probability alongside each generated weather row in `live.probs`. Before a model is ready or when features are incomplete, the internal probability can be NaN. The status endpoint converts an unavailable current probability to `0.0`; other endpoints may represent missing values as JSON `null`.

When pairing rows and probabilities, the backend slices them together and uses their shared order. Code that changes retention or reset behavior must preserve this alignment.

## 5. Model store

The module-level `store` dictionary tracks:

- `models`: trained model wrappers, or `None` before readiness;
- `metrics`: metrics generated during training;
- `medians`: feature medians used by model explanation logic;
- `ready`: whether models are available;
- `error`: internal training error information, if any;
- `training`: whether a training worker is active.

The serialized cache stores the scikit-learn version with models, metrics, and medians. It is a generated runtime artifact, not the canonical source for model implementation.

## 6. Location record

The current location record contains a human-readable name, latitude, longitude, and source label. It configures the synthetic generator. It is not a geocoded observation or a weather-provider response.

## 7. Frontend device state

`src/useDevice.js` combines backend status with frontend alert logic. The returned state includes the visible level, probability, rain state, readings, pressure trend, connection status, update time, model readiness, scenario, and supporting metadata.

The visible `level` is not sent by the backend as a final alert classification. It is evaluated in the browser using sensitivity thresholds, consecutive readings, rain state, and offline state.

## 8. Session event record

`src/sessionLog.js` records interaction events with:

- `t_ms`: elapsed milliseconds since the module initialized;
- `at`: local clock time formatted for display;
- `action`: event identifier;
- `detail`: string form of the event detail.

The array is held in browser memory and exported to CSV on request. It is not a backend event table.

## Data integrity rules

- Keep the feature order identical during training and inference.
- Keep weather rows and probability rows aligned by index.
- Do not use future weather values when computing current features.
- Do not mark an incomplete future target window as a negative example.
- Keep synthetic provenance attached to history and evaluation outputs.
- Do not confuse frontend alert level with the model's raw probability.
