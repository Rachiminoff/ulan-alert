# Implementation Decisions and Rationale

This document explains important choices visible in the current implementation. It is not a record of every historical discussion or an assertion that a choice is universally best. Each item describes the current behavior, the practical reason it matters, and the trade-offs a maintainer should preserve or reconsider deliberately.

## 1. The application is explicitly a synthetic simulation

The backend identifies itself as a synthetic weather simulation. Its weather readings are generated by `SyntheticWeather`; they are not readings from a deployed physical sensor network or a live weather service. The frontend also labels the experience as synthetic and not an official forecast.

**Why this matters:** users may reasonably interpret weather numbers as real-world observations. The simulation label prevents demonstration data from being mistaken for operational meteorological information.

**Maintenance rule:** new screens, exports, API responses, and screenshots should retain this distinction. Do not describe synthetic readings as live sensor measurements or model outputs as official forecasts.

## 2. Feature engineering has one shared implementation

`backend/features.py` defines `FEATURES`, `DEFINITIONS`, and `compute_features()`. Both model training and live inference use this function.

**Why this matters:** if training and production inference calculate a feature differently, the model receives inputs with different meanings. This is commonly called *training-serving skew*.

**Trade-off:** feature changes must be made carefully because they affect training, live predictions, feature descriptions, and any client that displays the feature list.

**Maintenance rule:** do not duplicate feature formulas in `main.py`, the frontend, or a notebook and treat the duplicate as authoritative. Update the shared function and its tests/documentation together.

## 3. The prediction target is a defined 30-minute event

`backend/features.py` sets `HORIZON = 30`. `future_wet_label()` labels a row positive when the rain indicator becomes true at any point in the following 30 simulated minutes. The prediction-versus-reality endpoint uses the same 30-minute horizon and excludes rows whose outcome window has not elapsed.

**Why this matters:** a probability is meaningful only when its target event and time window are clear. A probability for rain within 30 minutes is not interchangeable with a probability for rain within five minutes or an entire day.

**Maintenance rule:** changing the horizon is a research/model change, not merely a display adjustment. Update training labels, evaluation logic, user-facing wording, and documentation together.

## 4. Simulation advancement belongs to a background ticker

The FastAPI lifespan starts `_ticker()`. That task sleeps for `TICK_SECONDS` and advances the shared `live` simulation under a lock. GET endpoints read state rather than advancing it.

**Why this matters:** if a page refresh or a second browser tab advanced the simulation, the demonstration would run at different speeds depending on how many clients were connected. A single ticker gives the simulation one shared clock.

**Trade-off:** all clients connected to one backend process observe the same simulation state. This is not an isolated simulation session per visitor.

## 5. Shared mutable simulation state is protected by a lock

The module-level `live` object and `store` are shared by API handlers and the ticker/training worker. The implementation uses a re-entrant thread lock around important reads and writes.

**Why this matters:** requests and background work can overlap. Without coordination, a handler could read partially updated state or two actions could modify the simulation simultaneously.

**Maintenance rule:** when adding a route that reads or changes shared simulation/model state, review whether it needs the same lock. Keep lock-held work as short as practical; avoid slow network calls while holding it.

## 6. Model training does not block application startup

The FastAPI lifespan starts `_load_or_train()` in a daemon thread. A compatible cached model is loaded when available; otherwise `ml.train_all()` runs and the resulting model bundle is saved under `backend/.cache/model.joblib`. The API exposes readiness through status and metrics responses.

**Why this matters:** model training may take longer than starting an HTTP server. Running it in a background thread allows the service to start and report that the model is not ready yet.

**Trade-off:** an API response can arrive before the model is ready. The frontend and users must not assume model readiness immediately after the server responds.

## 7. Cache compatibility is tied to scikit-learn version

The cache stores the installed `sklearn.__version__` alongside models, metrics, and medians. The loader only accepts the cache when its stored version matches the currently installed version; otherwise it falls back to training.

**Why this matters:** serialized model objects can be incompatible across library versions.

**Maintenance rule:** if the cache format changes, update both the writer and loader. Treat cache files as generated artifacts, not source-controlled canonical model definitions.

## 8. The live probability and the warning state are separate concepts

The backend returns a probability. The frontend hook in `src/useDevice.js` applies user-selected watch/warning thresholds and a consecutive-reading rule to determine the visible state. It also handles offline state and a local alert cooldown.

**Why this matters:** a model score is a numeric estimate; a warning is a user-interface decision based on that estimate plus operating rules. Keeping these concepts separate makes it possible to tune alert sensitivity without silently changing the model itself.

**Maintenance rule:** document threshold changes and keep the labels consistent across settings, status cards, and research views. Do not describe a threshold as a model retraining parameter unless the model actually uses it.

## 9. The simulator and the frontend use different clocks

The backend advances simulated minutes according to its ticker and speed setting. The browser polls `/api/status` on a two-second interval and records a local `updatedAt` time when a response is processed. The displayed connection age is therefore a browser-side freshness indicator, not a simulated-weather duration.

**Why this matters:** a faster simulation can advance several simulated minutes between browser polls. A two-second polling interval does not mean the simulation advances by exactly two minutes.

## 10. Location configures the synthetic environment; it is not a live data lookup

`POST /api/location` stores a name and valid latitude/longitude on the shared simulation. When coordinates change, the simulation is reset. The simulator uses location-related calculations such as daylight and seasonal wetness.

**Why this matters:** the location affects generated conditions, but it does not cause the app to fetch real weather for that location.

## 11. Session interaction logs are browser-local

`src/sessionLog.js` stores events in an in-memory array for the current page session and can export them as CSV. It does not persist them to the backend or across browser restarts.

**Why this matters:** a reload clears the in-memory event history. The export is a usability/session artifact, not a permanent audit log.

## 12. The frontend build is served by the backend when available

The backend serves `dist/index.html` at `/` and static assets through the final catch-all route. If the build does not exist, `/` returns a small API information response instead.

**Why this matters:** local development can use Vite while a packaged deployment can serve the compiled frontend and API from one origin. The catch-all route is deliberately last so API routes are matched first.

## Change-impact checklist

Before changing a behavior, ask:

- Does it change the synthetic-data boundary or how the app describes its readings?
- Does it change feature calculations shared by training and inference?
- Does it change the 30-minute target or evaluation window?
- Does it affect shared state, the ticker, or lock usage?
- Does it affect model cache compatibility or readiness behavior?
- Does it change alert thresholds, consecutive-reading behavior, or cooldown?
- Does it change location reset behavior or browser-local persistence?
- Do the tests, examples, and documentation need to change with it?
